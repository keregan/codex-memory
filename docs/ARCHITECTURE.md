# Архитектура Codex Memory

## Принципы

1. Исходная история неизменяема.
2. `memory.json` — единственный канонический формат состояния.
3. Markdown всегда строится из согласованного JSON.
4. Неоднозначность сохраняется как `[NEEDS_REVIEW]`, а не заполняется догадкой.
5. Сетевой LLM используется только после явного выбора пользователя.

## Компоненты

### `history_reader.py`

Читает UTF-8/CP1251 и разбивает текст на пронумерованные блоки. Когда возможно, извлекает дату и роль автора.

### `analyzer.py`

Содержит общий интерфейс анализатора и две реализации:

- `RuleBasedAnalyzer` — полностью локальный консервативный fallback;
- `LLMAnalyzer` — структурированное извлечение через настроенный Chat Completions endpoint.

История рассматривается как недоверенный материал. Команды внутри неё не должны влиять на поведение анализатора.

Сетевой клиент ограничивает размер ответа, использует конечный timeout и выполняет ограниченные повторы с exponential backoff только для временных сетевых ошибок и HTTP `429`, `502`, `503`, `504`.

### `chunking.py`

Перед сетевым анализом сообщения упаковываются в упорядоченные неперекрывающиеся блоки с мягким лимитом символов. Очень большое одиночное сообщение делится по строке или слову, сохраняя исходный номер сообщения. Проекты из разных блоков объединяются по безопасному имени, а извлечённые знания — в хронологическом порядке.

### `models.py`

Определяет сообщения, проекты, версию схемы и границу валидации результата анализатора. Неизвестные поля отбрасываются, confidence и номера источников нормализуются.

### `schema.py`, `schemas/memory.schema.json`, `migrations.py`

JSON Schema Draft 2020-12 формально описывает канонический документ. Runtime-валидатор не требует сторонних библиотек и проверяет те же основные инварианты. Миграции выполняются последовательно; версия 1 преобразуется в версию 2 с добавлением `created_at`. Чтение не переписывает старый файл: мигрированный документ сохраняется только при успешном `--update`.

### `reconciler.py`

Объединяет новое извлечение с существующей памятью. Перемещает задачи между статусами, сохраняет историю решений и обрабатывает явные миграции технологий.

### `markdown_renderer.py`

Не принимает решений. Только воспроизводимо отображает согласованный `memory.json` в четыре Markdown-файла.

### `storage.py`

Проверяет схему и принадлежность существующей памяти проекту. Новый каталог полностью собирается в sibling staging-каталоге. При обновлении старый каталог переименовывается в backup, staging становится рабочим каталогом, а при исключении старый каталог возвращается на место. Неуправляемые дополнительные файлы проекта копируются в staging и сохраняются.

Перед копированием существующего каталога хранилище рекурсивно отклоняет символические ссылки и Windows reparse points. Это не позволяет управляемому файлу в staging перенаправить запись за пределы каталога памяти.

На время чтения и записи удерживается файловая блокировка ОС: `msvcrt` в Windows и `flock` в POSIX-системах. Она не позволяет конфликтующим операциям выполняться одновременно и автоматически освобождается ОС при аварийном завершении процесса. Перед записью CLI под блокировкой сравнивает текущее состояние с прочитанным ранее и отклоняет устаревшее обновление. Фазы directory swap записываются в атомарно заменяемый журнал. Восстановление выполняется перед чтением и записью: незавершённая замена либо откатывается к backup, либо завершается очисткой уже активированного каталога.

### `cli.py`

Управляет потоком выполнения. Все проекты анализируются и валидируются до начала записи, чтобы ошибка анализа одного проекта не оставляла остальные частично обновлёнными.

## Формат обновления

`--update` загружает существующий `memory.json`, применяет извлечённые изменения и заново генерирует Markdown. Markdown не разбирается обратно и не является источником истины.

Текущая версия схемы — 2. История обновлений сохраняет только пользовательские операции `create` и `update`; техническая миграция не изображается как новое знание проекта.

## Будущие улучшения

- более строгая модель evidence и противоречий;
- иерархическое или LLM-объединение результатов чанков;
- общая транзакция для пакетного обновления нескольких проектов;
- property-based и mutation testing;
- поддержка дополнительных экспортных форматов.
