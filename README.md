# Codex Memory

Локальная система, которая превращает длинную смешанную историю общения с AI coding-агентом в компактную актуальную память по проектам.

> Статус: рабочий MVP, версия 0.3. Формат `memory.json` версионируется и автоматически мигрирует поддерживаемые старые версии.

## Что создаётся

Для каждого найденного проекта программа создаёт каталог `memory/<project>/`:

- `memory.json` — каноническое machine-readable состояние;
- `PROJECT_CONTEXT.md` — назначение, стек, архитектура и ограничения;
- `DECISIONS.md` — актуальные и заменённые решения;
- `TASKS.md` — текущие, будущие и выполненные задачи, известные баги;
- `AGENTS.md` — команды и правила для coding-агента.

Исходная история открывается только для чтения. Существующая память не изменяется без флага `--update`.

## Требования

- Python 3.10 или новее;
- дополнительные Python-пакеты не требуются;
- режим буфера обмена поддерживается в Windows.

## Быстрый старт

Обработка файла:

```powershell
python main.py history.txt
```

Поддерживаются обычный текст (`.txt`), Markdown с заголовками ролей (`.md`), JSON,
JSONL и NDJSON. Для JSON поддерживаются списки сообщений, объекты с `messages`
и древовидные экспорты с `mapping`/`current_node`. В древовидном экспорте
обрабатывается только активная ветка диалога. UTF-8 и CP1251 определяются
автоматически; исходный файл всегда остаётся неизменным.

Обработка текста из буфера обмена в Windows:

```powershell
python main.py --clipboard
```

Неинтерактивный запуск с явно заданными проектами:

```powershell
python main.py history.txt --projects telegram_bot,personal_site --yes
```

Обновление существующей памяти:

```powershell
python main.py history_new.txt --update --projects telegram_bot --yes
```

При обработке нескольких проектов анализ и валидация всех результатов завершаются до начала записи. Во время записи каждый проект является отдельной транзакцией: ошибка одного проекта отображается как `ERROR`, остальные подготовленные проекты продолжают сохраняться. При частичном результате программа возвращает код `2` и сообщает число успешных и неуспешных записей.

Все параметры:

```powershell
python main.py --help
```

При работе через LLM большие истории автоматически разбиваются на блоки. Результаты блоков объединяются многоуровневым детерминированным reduce: одинаковые элементы дедуплицируются, evidence-поля объединяются, а поздний надёжный статус задачи заменяет ранний. Размер блока можно настроить:

```powershell
python main.py history.txt --provider llm --chunk-chars 50000
```

Минимальное значение — 1000 символов. Сообщение крупнее одного блока дополнительно делится по ближайшей границе строки или слова.

## Режимы анализа

### Локальные правила

Используются по умолчанию, не требуют сети и не отправляют историю наружу. Этот анализатор намеренно консервативен: результаты с `MEDIUM`, `LOW` и `[NEEDS_REVIEW]` следует проверить.

### Явно настроенный LLM API

Сетевой запрос выполняется только при выборе `--provider llm`:

```powershell
$env:CODEX_MEMORY_API_URL = "http://localhost:11434/v1/chat/completions"
$env:CODEX_MEMORY_MODEL = "your-model"
python main.py history.txt --provider llm
```

Если сервис требует ключ, задайте `CODEX_MEMORY_API_KEY` через переменную окружения. Не передавайте ключ в командной строке и не сохраняйте его в репозитории.

Сетевой клиент ограничивает ответ двумя MiB и повторяет временно неуспешный запрос до двух раз. Значения можно изменить явно:

```powershell
python main.py history.txt --provider llm --llm-timeout 120 --llm-retries 2 --llm-max-response-bytes 2097152
```

Повторяются только сетевые ошибки и ответы HTTP `429`, `502`, `503`, `504`. Заголовок `Retry-After` учитывается, максимальная задержка ограничена 30 секундами.
Повторный запрос может повторно учитываться провайдером в использовании API, поэтому число попыток намеренно ограничено.

## Приватность и безопасность

- типовые имена историй (`history*`, `chat*`, `transcript*`, `conversation*`),
  каталог `exports/`, `memory/`, `.env`, ключи и локальные базы исключены из Git;
- имена проектов очищаются до использования в путях;
- ответы LLM валидируются перед сохранением;
- символические ссылки и Windows reparse points внутри каталога проекта отклоняются перед записью;
- `memory.json` проверяется по правилам формальной JSON Schema версии 3;
- память версий 1 и 2 последовательно мигрирует в версию 3 при следующем обновлении;
- факты, задачи и решения имеют стабильные ID, статус и историю evidence с источником, блоками и временем наблюдения;
- нечёткое объединение задач и решений использует консервативный порог, а явно конфликтующий факт можно сохранить со статусом `disputed`;
- сообщения истории считаются недоверенными данными, а не инструкциями для модели;
- весь каталог проекта собирается рядом в staging-каталоге и заменяется через directory swap с rollback при ошибке;
- параллельные записи одного проекта блокируются, а незавершённая directory-swap транзакция восстанавливается при следующем запуске;
- перед записью проверяется, что память не изменилась после чтения, поэтому устаревший процесс не затирает более новое обновление;
- публикация репозитория не должна включать реальные истории или сгенерированную память.

Перед первым `git push` обязательно выполните проверки из раздела «Публикация».

## Тесты

```powershell
python -m unittest discover -s tests -v
python -m compileall -q main.py codex_memory tests
```

Тесты покрывают импорт текстовых, Markdown, JSON/JSONL и древовидных историй, чанкинг, анализаторы, JSON Schema и миграции, согласование обновлений, rollback каталога, безопасность путей, CLI и базовый поиск секретов. GitHub Actions запускает их на Windows и Linux.

## Архитектура

Поток данных:

```text
history / clipboard
        ↓
history_reader
        ↓
project detector → подтверждение проектов
        ↓
knowledge extractor
        ↓
reconciler + existing memory.json
        ↓
validated memory.json → Markdown renderer
```

Подробности находятся в [docs/ARCHITECTURE.md](docs/ARCHITECTURE.md).

## Известные ограничения

- эвристический анализатор не заменяет полноценное семантическое понимание;
- иерархическое объединение чанков детерминировано и не выполняет отдельный финальный LLM-проход;
- повреждённый вручную журнал транзакции требует вмешательства пользователя;
- атомарность гарантируется на уровне одного проекта; при пакетном запуске CLI явно сообщает о частичном результате;
- автоматическое разрешение сложных противоречий требует проверки человеком.
